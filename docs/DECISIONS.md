# Decisions log

Format: `D-0xx — title`. Context → decision → consequence. Newest at the bottom. PRD §4 choices come first.

## Stack (from PRD §4)

**D-001 — Next.js (App Router) + TypeScript.** One codebase for staff app, public customer link and server logic. Server Actions and server components keep secrets on the server. Version: Next 16.4 (current stable at build time).

**D-002 — Supabase (Postgres + Auth).** The domain is relational (customer → vehicles → jobs → lines/events). Row Level Security enforces role isolation inside the database, so a UI bug cannot leak another mechanic's job.

**D-003 — Tailwind v4 + shadcn/ui-style components.** Accessible primitives, fast to build, no runtime CSS-in-JS.

**D-004 — Vercel (app) + Supabase (DB).** Zero-ops deploys, preview URLs, env vars kept outside the repo. Hobby tier: no paid features (e.g. no Vercel WAF rate limiting), see D-012.

**D-005 — Vitest + Playwright.** Vitest covers money logic and DB integration (RLS, `transition_job`, revenue). Playwright covers the full flow, including a 375px phone viewport.

**D-006 — GitHub Actions CI: lint, typecheck, unit, integration, e2e.** Integration and e2e run against a throwaway local Supabase stack (`supabase start`) in CI, never against production.

## Build decisions

**D-007 — `cacheComponents` / partial prefetching disabled.** create-next-app 16 enables them by default. Every staff page is per-user (auth cookie) and the public page must be `no-store`, so cached components add Suspense boilerplate and risk caching personal data with no benefit.

**D-008 — Status enum values.** `new, quoted, approved, in_progress, ready, collected` (Postgres enum `job_status`). Labels in UI: New, Quoted, Approved, In progress, Ready, Collected.

**D-009 — One state machine, two entry modes.** `transition_job(p_job_id uuid, p_to_status job_status, p_note text default null, p_link_token_hash text default null)` is the only code that changes `jobs.status`.
- Staff mode (`p_link_token_hash` null): actor = `auth.uid()`, must be an active profile; owner or the assigned mechanic.
- Customer mode (`p_link_token_hash` given): callable only with the service role (server-side, after the token was hashed). The function re-checks that the hash belongs to an active link of that job, inside the same transaction. Actor = customer, `actor_id` null. Only `quoted→approved` and `quoted→new` are allowed.
- The row is locked `FOR UPDATE`; validation, job update and the single `job_events` insert happen in one transaction. Invalid transitions raise `invalid_transition` and write nothing.
- Customer calls are idempotent: approve when already approved (or later) and decline when already `new` return the current job with no new event.
- Direct `UPDATE` of `status`, `quoted_*`, `approved_*`, `collected_at` is revoked from `authenticated` with column privileges, so the function is the only path.

**D-010 — Revert to `new` clears `quoted_*`.** On decline or "Revise quote", `quoted_subtotal/vat/total_cents` and `quoted_at` are set to null (stale), lines unlock. The event row keeps who/why. Re-quoting freezes fresh values.

**D-011 — Totals in one place.** `public.compute_job_totals(job_id)` (used by the `job_totals` view, security invoker) returns live subtotal/VAT/total from line items and the job's `vat_bps` snapshot. Quoting copies it into `quoted_*`. UI shows live totals for `new` jobs and frozen `quoted_*` afterwards.

**D-012 — Rate limiting without paid infra.** Vercel Hobby has no rate-limit rules and serverless memory is per instance, so limits live in Postgres: `rate_limit_hit(key, max, window_seconds)` (service role only, fixed window). Key = SHA-256 of client IP + bucket. Public page: 60 req/min/IP; approve/decline: 10/min/IP. Over the limit → same generic 404 page with status 429.

**D-013 — Token, hash and lookup.** 32 random bytes (`crypto.randomBytes`) → base64url (43 chars). Only `sha256(token)` as lowercase hex is stored (`job_links.token_hash`, unique). One active link per job (partial unique index where `revoked_at is null`); "Regenerate" revokes the old one in the same DB call (`create_job_link`). Lookup by hash is a single indexed equality, done for every single-segment URL, so valid/invalid/revoked tokens cost the same and all fall through to the same `notFound()`.

**D-014 — Public DTO built in the database.** `public_job_by_token_hash(hash)` (security definer, execute granted to `service_role` only) returns a JSON object with exactly the PRD §6 FR6 whitelist. The TS mapper re-picks the same keys and a test asserts the key set. Customer first name = first word of `full_name`. Public timeline = status + timestamp only (no notes, no actors).

**D-015 — Link lifetime.** A link is valid while `revoked_at is null` and the job is not collected more than 30 days ago (PRD Q6). Links can be created/regenerated by the owner or assigned mechanic when the job status is `quoted`, `approved`, `in_progress` or `ready` (not `new`: nothing to show; not `collected`).

**D-016 — Seed inserts history directly.** Realistic timelines need backdated timestamps that `transition_job` (which uses `now()`) cannot produce. The seed script (service role) inserts jobs/events directly, keeping them consistent with the state machine, and computes `quoted_*` via `compute_job_totals`. App code never does this.

**D-017 — Normalised search fields.** Triggers normalise on write: `customers.phone` digits only, `vehicles.plate` uppercase with spaces/dashes removed (stored normalised; formatted `ABC 1234` for display). Search uses `pg_trgm` GIN indexes and `ilike` on name, phone digits and plate.

**D-018 — Profiles readable by all active staff.** Timelines show which staff member acted, so mechanics can read `profiles(id, full_name, role)` of colleagues. No emails are stored there. Settings, customer directory and dashboard stay owner-only.

**D-019 — Security headers on every HTML response.** `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` (except `/_next/static`), plus CSP, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Permissions-Policy`. Applying them everywhere (not only on the token route) means a valid link, an invalid link and any other unknown URL produce byte-identical 404s.

**D-020 — Access denied = 404 for staff-only areas.** A mechanic opening `/dashboard`, `/settings` or `/customers` gets the generic not-found page, and the underlying DB functions/RLS return nothing. Same behaviour as another mechanic's job (FR1 AC), and it does not confirm the page exists.

**D-021 — VAT rate shown on the customer page.** The FR6 whitelist lists "subtotal, VAT, total". The DTO also carries `totals.vat_bps` so the page can say "VAT (12%)". It is public pricing information, not personal data.

**D-022 — Next pinned to 16.4.3.** pnpm 11's supply-chain policy (`minimumReleaseAge`) rejected 16.4.4, published the same day. Pinned the previous patch instead of relaxing the policy. Bump after the cutoff passes.

**D-023 — Customer page while a quote is being revised.** When a declined/revised job is back in `new`, the DTO has `lines: []` and `totals: null`, and the page shows "Your quote is being revised" with no buttons. Customers never see half-edited lines.
