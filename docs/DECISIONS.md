# Decisions log

Format: `D-0xx — title`. Context → decision → consequence. Newest at the bottom. PRD §4 choices come first.

## Stack (from PRD §4)

**D-001 — Next.js (App Router) + TypeScript.** One codebase for staff app, public customer link and server logic. Server Actions and server components keep secrets on the server. Version: Next 16.4 (current stable at build time).

**D-002 — Supabase (Postgres + Auth).** The domain is relational (customer → vehicles → jobs → lines/events). Row Level Security enforces role isolation inside the database, so a UI bug cannot leak another mechanic's job.

**D-003 — Tailwind v4 + shadcn/ui-style components.** Accessible primitives, fast to build, no runtime CSS-in-JS.

**D-004 — Vercel (app) + Supabase (DB).** Zero-ops deploys, preview URLs, env vars kept outside the repo. Hobby tier: no paid features (e.g. no Vercel WAF rate limiting), see D-012.

**D-005 — Vitest + Playwright.** Vitest covers money logic and DB integration (RLS, `transition_job`, revenue). Playwright covers the full flow, including a 375px phone viewport.

**D-006 — GitHub Actions CI: lint, typecheck, unit, integration, e2e.** Integration and e2e run against a throwaway local Supabase stack (`supabase start`) in CI, never against production.

## Build decisions

**D-007 — `cacheComponents` / partial prefetching disabled.** create-next-app 16 enables them by default. Every staff page is per-user (auth cookie) and the public page must be `no-store`, so cached components add Suspense boilerplate and risk caching personal data with no benefit.

**D-008 — Status enum values.** `new, quoted, approved, in_progress, ready, collected` (Postgres enum `job_status`). Labels in UI: New, Quoted, Approved, In progress, Ready, Collected.

**D-009 — One state machine, two entry modes.** `transition_job(p_job_id uuid, p_to_status job_status, p_note text default null, p_link_token_hash text default null)` is the only code that changes `jobs.status`.
- Staff mode (`p_link_token_hash` null): actor = `auth.uid()`, must be an active profile; owner or the assigned mechanic.
- Customer mode (`p_link_token_hash` given): callable only with the service role (server-side, after the token was hashed). The function re-checks that the hash belongs to an active link of that job, inside the same transaction. Actor = customer, `actor_id` null. Only `quoted→approved` and `quoted→new` are allowed.
- The row is locked `FOR UPDATE`; validation, job update and the single `job_events` insert happen in one transaction. Invalid transitions raise `invalid_transition` and write nothing.
- Customer calls are idempotent: approve when already approved (or later) and decline when already `new` return the current job with no new event.
- Direct `UPDATE` of `status`, `quoted_*`, `approved_*`, `collected_at` is revoked from `authenticated` with column privileges, so the function is the only path.

**D-010 — Revert to `new` clears `quoted_*`.** On decline or "Revise quote", `quoted_subtotal/vat/total_cents` and `quoted_at` are set to null (stale), lines unlock. The event row keeps who/why. Re-quoting freezes fresh values.

**D-011 — Totals in one place.** `public.compute_job_totals(job_id)` (used by the `job_totals` view, security invoker) returns live subtotal/VAT/total from line items and the job's `vat_bps` snapshot. Quoting copies it into `quoted_*`. UI shows live totals for `new` jobs and frozen `quoted_*` afterwards.

**D-012 — Rate limiting without paid infra.** Vercel Hobby has no rate-limit rules and serverless memory is per instance, so limits live in Postgres: `rate_limit_hit(key, max, window_seconds)` (service role only, fixed window). Key = SHA-256 of client IP + bucket. Public page: 60 req/min/IP; approve/decline: 10/min/IP. Over the limit: page views get the same generic 404 (so limits do not reveal which URLs are real); approve/decline get a "too many attempts" message.

**D-013 — Token, hash and lookup.** 32 random bytes (`crypto.randomBytes`) → base64url (43 chars). Only `sha256(token)` as lowercase hex is stored (`job_links.token_hash`, unique). One active link per job (partial unique index where `revoked_at is null`); "Regenerate" revokes the old one in the same DB call (`create_job_link`). Lookup by hash is a single indexed equality, done for every single-segment URL, so valid/invalid/revoked tokens cost the same and all fall through to the same `notFound()`.

**D-014 — Public DTO built in the database.** `public_job_by_token_hash(hash)` (security definer, execute granted to `service_role` only) returns a JSON object with exactly the PRD §6 FR6 whitelist. The TS mapper re-picks the same keys and a test asserts the key set. Customer first name = first word of `full_name`. Public timeline = status + timestamp only (no notes, no actors).

**D-015 — Link lifetime.** A link is valid while `revoked_at is null` and the job is not collected more than 30 days ago (PRD Q6). Links can be created/regenerated by the owner or assigned mechanic when the job status is `quoted`, `approved`, `in_progress` or `ready` (not `new`: nothing to show; not `collected`).

**D-016 — Seed inserts history directly.** Realistic timelines need backdated timestamps that `transition_job` (which uses `now()`) cannot produce. The seed script (service role) inserts jobs/events directly, keeping them consistent with the state machine, and computes `quoted_*` via `compute_job_totals`. App code never does this.

**D-017 — Normalised search fields.** Triggers normalise on write: `customers.phone` digits only, `vehicles.plate` uppercase with spaces/dashes removed (stored normalised; formatted `ABC 1234` for display). Search uses `pg_trgm` GIN indexes and `ilike` on name, phone digits and plate.

**D-018 — Profiles readable by all active staff.** Timelines show which staff member acted, so mechanics can read `profiles(id, full_name, role)` of colleagues. No emails are stored there. Settings, customer directory and dashboard stay owner-only.

**D-019 — Security headers on every HTML response.** `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` (except `/_next/static`), plus CSP, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Permissions-Policy`. Applying them everywhere (not only on the token route) means a valid link, an invalid link and any other unknown URL produce byte-identical 404s.

**D-020 — Access denied = 404 for staff-only areas.** A mechanic opening `/dashboard`, `/settings` or `/customers` gets the generic not-found page, and the underlying DB functions/RLS return nothing. Same behaviour as another mechanic's job (FR1 AC), and it does not confirm the page exists.

**D-021 — VAT rate shown on the customer page.** The FR6 whitelist lists "subtotal, VAT, total". The DTO also carries `totals.vat_bps` so the page can say "VAT (12%)". It is public pricing information, not personal data.

**D-022 — Next pinned to 16.4.3.** pnpm 11's supply-chain policy (`minimumReleaseAge`) rejected 16.4.4, published the same day. Pinned the previous patch instead of relaxing the policy. Bump after the cutoff passes.

**D-023 — Customer page while a quote is being revised.** When a declined/revised job is back in `new`, the DTO has `lines: []` and `totals: null`, and the page shows "Your quote is being revised" with no buttons. Customers never see half-edited lines.

**D-024 — Insert triggers apply to every role, the seed included.** A new job always lands in `new` with `vat_bps` copied from settings and `quoted_*`/`approved_*`/`collected_at` null; its `null→new` event copies `jobs.created_at`. Labour lines take `settings.hourly_rate_cents` at insert. Line writes take `FOR SHARE` on the job row, so they serialise with `transition_job`'s `FOR UPDATE` and no line can slip into a quote while it is being frozen. Consequence for D-016: the seed inserts the job (it may set `created_at`/`created_by`), adds lines while it is `new` (setting the hourly rate first for an old-rate job), then updates status/`quoted_*`/`approved_*`/`collected_at` and inserts later events directly as service role.

**D-025 — Error messages beyond the shared contract.** `invalid_mechanic` (assignee is not an active mechanic), `not_linkable` (link on a `new`/`collected` job), `invalid_token_hash`, `kind_immutable`, `invalid_argument` (`rate_limit_hit`). Signed-in users without an active profile get `forbidden`; a mechanic touching another mechanic's job gets `not_found`, including line inserts (checked before RLS so the job's status never leaks). Transition notes are trimmed and cut to 500 characters instead of rejected, so a long decline reason never blocks a customer.

**D-026 — `job_events.id` is a bigint identity.** Timeline order is `(created_at, id)`, which stays stable when two events share a timestamp.

**D-027 — Dashboard JSON shape.** `revenue.month_end` is exclusive (first instant of next month in the garage timezone). `counts_by_status` always has all 6 keys. `workload` lists every active mechanic by name with `by_status` holding the 5 open statuses (zeros included). `ready_jobs` is ordered longest-waiting first; `days_waiting` = calendar days in the garage timezone between the latest `→ready` event and `p_now`.

**D-028 — Mechanic visibility via set-returning helpers.** Customer/vehicle policies use `id in (select private.my_customer_ids())` / `my_vehicle_ids()` (security definer, active mechanic only). One permissive policy per table and action, no RLS recursion, and inactive staff see nothing.

**D-029 — Default privileges.** Per-schema `revoke` from `anon` on tables, sequences and functions in `public`, plus a global `alter default privileges revoke execute on functions from public` (role `postgres`): PUBLIC's EXECUTE is a global default that a per-schema rule cannot remove. Every new function needs explicit grants; an extension created later by `postgres` will not be PUBLIC-executable, so grant it explicitly.

**D-030 — Rate-limit housekeeping.** `rate_limit_hit` accepts windows of 1–3600 s and deletes rows older than 1 hour on every call, which is safe for every key given that cap.

**D-031 — Small schema contracts for the app.** `jobs.vat_bps` has `default 0` only so the generated Insert type marks it optional (clients may not write it; the trigger sets it). `job_line_items.unit_price_cents` has no default: parts must state a price; for labour the client may send any value (e.g. 0) and the trigger replaces it. `vehicles.year` is nullable; `customers.email` is optional with a minimal `x@y` check. The `job_links` column grant excludes `token_hash`, so clients must list columns (`select('*')` fails). `search_customers('')` returns every visible customer; `vehicles` items are `{id, plate, make, model, year}`; phone matching needs at least 3 digits. `jobs.ref` comes from `next_job_ref()`: `GD-0001`…`GD-9999`, then `GD-10000` (pads, never truncates).

**D-032 — "Identical 404" means identical apart from Next's echo of the request.** Next's 404 payload carries a per-request nonce and echoes the requested path. Both come from the attacker's own request, so they reveal nothing about whether a token exists. Tests normalise those two before comparing bodies; status, headers and all page content are identical.

**D-033 — Sign-in checks the profile is active.** After a successful password check, `signIn` reads the user's own profile; inactive or profile-less accounts are signed out again and see the same generic "Email or password is incorrect." message, instead of bouncing silently between `/` and `/login`.

**D-034 — Server action error contract.** Actions return only sentences from `src/lib/data/errors.ts`: DB errors are matched by exact message (`invalid_transition`, `forbidden`, `not_found`, `no_line_items`, `job_locked`, `invalid_mechanic`, `not_linkable`, `kind_immutable`) or code `42501`, everything else becomes the action's fallback sentence, so raw DB text never reaches the UI. An update/delete that matches zero rows (RLS hides rows silently) returns "This line no longer exists". Data functions (`getJob`, `listJobs`, …) throw a generic error on DB failure (error boundary) instead of returning `null`, so an outage is not shown as a 404; `getJob` returns `null` only for a malformed id, a missing job or one RLS hides. Owner-only data functions call `requireOwner()` (mechanics get the 404, D-020).

**D-035 — Line form contract.** `quantity` is parsed with `parseQuantity` (≤ 8+2 digits, so `Number()` round-trips it exactly into `numeric(10,2)`); lines are read back as `quantity::text` (`"1.50"`). Labour lines send `unit_price_cents = 0` and the trigger sets the rate (D-031). `updateLine` treats `unit_price` as "change the price": present means it must be a valid euro amount, absent keeps the current price, so labour edit forms must omit the field. Descriptions: job ≤ 2,000 chars, line ≤ 500, notes/decline reasons ≤ 500 (validated with a message rather than silently cut; the DB still truncates as a backstop, D-025).

**D-036 — Customer approve/decline flow.** Order: rate limit (`publicAction`, 10/min/IP) → token shape check (43 base64url chars) → SHA-256 → service-role lookup of the active link's `job_id` by hash → `transition_job(…, p_link_token_hash)`, which re-checks the link and the 30-day expiry in its own transaction. Unknown, revoked or expired tokens all return "This link is no longer valid."; a quote that is no longer `quoted` returns a "refresh to see the current status" sentence. The raw token is only in the `createCustomerLink` response and in `revalidatePath('/<token>')`; it is never logged. Link base URL: `NEXT_PUBLIC_SITE_URL`, else the request's `Origin`.

**D-037 — Customer approval is bound to the quote the customer saw.** `transition_job` takes a 5th argument, `p_expected_total_cents`. In customer mode, `quoted → approved` requires it to equal the frozen `quoted_total_cents`, else `quote_changed` with no event and no change (`approveQuote` sends the page's hidden `expected_total_cents`; a missing or malformed value gets the same "The quote changed…" sentence without calling the DB). Idempotent replays (already approved or later) stay no-ops and need no total; decline needs none. Known limit: a re-quote with a different set of lines but exactly the same total still matches.

**D-038 — `transition_job` checks the caller before it reads or locks the job.** Customer mode (`p_link_token_hash` given) raises `forbidden` unless the caller is the service role; staff mode raises `forbidden` when `private.staff_role()` is null. Only then is the job selected `FOR UPDATE`, and for a mechanic the lookup itself filters on `assigned_mechanic_id`, so another mechanic's job is never locked and returns exactly `not_found`, like a missing id. A mechanic passing a link hash always gets `forbidden`, whether or not the job exists.

**D-039 — Staff can revoke a customer link in any status.** `revoke_job_link(p_job_id) → boolean` (security definer, `authenticated` only) uses the same caller checks as `create_job_link` (`forbidden` for no active profile, `not_found` for another mechanic's or a missing job), locks the job row, sets `revoked_at = now()` on the active link and returns whether one was revoked. Unlike creation it works in `new` and `collected` too. The `revokeCustomerLink` action treats "nothing to revoke" as success, so a double submit is harmless.

**D-040 — `next_job_ref()` lives in schema `private`.** It was callable through the API (`rpc('next_job_ref')`) and burned sequence values. Same body; `jobs.ref` defaults to `private.next_job_ref()`; `authenticated` and `service_role` get `EXECUTE` (and `service_role` gets `USAGE` on `private`) because the default runs as the inserting role.

**D-041 — Default privileges in `public` exclude `authenticated` too.** Extends D-029: future tables, sequences and functions created by `postgres` in `public` are not auto-granted to `authenticated` either, so every new object needs an explicit grant (as the existing migrations already do). `service_role` keeps Supabase's defaults.

**D-042 — Link tokens are generated in the app server, not the DB (accepted risk).** `createCustomerLink` generates the 32-byte token and sends only its SHA-256 to `create_job_link`. Staff who create a link hold the raw token by design (they send it to the customer); generating it in the DB would not change that, because the DB would have to return it to the same staff member. Mitigations: the token is shown once, never stored or logged, and staff can revoke it at any time (D-039).

**D-043 — Per-request nonce CSP in `src/proxy.ts`.** Every HTML response gets `script-src 'self' 'nonce-…' 'strict-dynamic'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, `form-action 'self'`, `upgrade-insecure-requests` (prod). Next.js reads the nonce from the request header and applies it to its own scripts, so pages that need it render dynamically (the 404 page awaits `connection()`). `style-src` keeps `'unsafe-inline'` because Next/React inject inline styles; no user HTML is ever rendered, so the residual risk is CSS-only. Static headers (noindex, no-referrer, no-store, nosniff, DENY, HSTS) stay in `next.config.ts`.

**D-044 — Auth cookies are `httpOnly`, `SameSite=Lax`, `Secure` in production.** There is no browser Supabase client (all data access is in server components and server actions), so JavaScript never needs the session tokens. The same options are used by the server client and the proxy refresh (`src/lib/supabase/cookie-options.ts`).

**D-045 — Sign-in is rate limited.** `signIn` uses the `login` bucket (10 attempts / 5 min per IP hash, D-012) before calling Supabase, and returns the same generic sentence for limit, bad password and inactive profile. Supabase Auth's own limits remain a second layer.

**D-046 — Secrets guard runs locally and in CI.** `.githooks/pre-commit` scans staged index blobs and `pre-push` scans all tracked files (`scripts/secrets-scan.mjs`); `pnpm install` points `core.hooksPath` at `.githooks`. The scan blocks env files, `.vercel/`, `CREDENTIALS.local.md`, `.auth/` storage states and keys, and any exact value from the local env files. Files holding plaintext passwords (`.env.local`, `CREDENTIALS.local.md`) are written with mode 0600. CI actions are pinned to commit SHAs and the Supabase CLI to the devDependency version; `pnpm bundle:scan` checks `.next/static` and prerendered HTML/RSC for server secrets after every build.

## Client answers (2026-11-02)

The client answered PRD §12. The entries below apply them; where they conflict with an earlier entry, the later entry wins.

**D-047 — Client answers adopted.** Superseded: D-010 (decline/revise no longer returns to `new`), D-015 (30-day link lifetime), D-020 for `/customers` (mechanics now use it), D-023 (a job never goes back to `new`), D-028 (mechanic visibility of customers/vehicles), D-037 (approval bound to the total → now bound to the quote version, which also removes D-037's "same total, different lines" gap). The PRD (§3, §5, FR2–FR9, §8, §12) was updated to match.

**D-048 — Exact line amounts, one rounding at the end.** `job_line_items.line_total_cents` is `numeric(16,2)` = `quantity × unit_price_cents`, never rounded (quantity has 2 decimals and prices are whole cents, so the product is exact). `compute_job_totals`: `net = round(Σ line_total)`, `vat = round(Σ line_total × vat_bps / 10000)`, `total = net + vat`, Postgres `round(numeric)` = half away from zero. VAT is taken from the exact sum, not the rounded net, so each figure is rounded exactly once; `total = net + vat` keeps every document adding up. Line amounts are displayed exactly (2–4 decimals, e.g. €56.875); net/VAT/total always 2 decimals.

**D-049 — Immutable quote versions.** Every move to `quoted` inserts `job_quotes(job_id, version, subtotal/vat/total_cents, vat_bps, lines jsonb snapshot, created_by, created_at)` and sets `jobs.quote_version` and `quoted_*`. Approvals (link or phone) must pass the version the approver saw (`p_expected_version`); a different version raises `quote_changed` and changes nothing. Approval copies the version's figures into `approved_quote_version`, `approved_subtotal_cents`, `approved_vat_cents`, `approved_total_cents`, `approved_at`. `ready → collected` requires `approved_quote_version = quote_version`. Quote rows have no update/delete path (RLS select-only for staff on accessible jobs; writes only inside security-definer functions).

**D-050 — Automatic re-quote after a line change.** Lines are editable in `new`, `quoted`, `declined`, `approved`, `in_progress`; `ready`/`collected`/`cancelled` raise `job_locked`. A statement-level trigger after insert/update/delete on lines of a job in `quoted`, `approved` or `in_progress` calls the same transition logic: next quote version, status `quoted`, event actor = the staff member who edited, note "Lines changed — new quote". Removing the last line of such a job raises `no_line_items`. Enforcing this in the database means no code path can change an approved total without a new approval. Every change makes a version (simple and auditable); the UI groups consecutive revisions. In `new` and `declined` edits don't re-quote; staff press "Send quote"/"Send new quote".

**D-051 — Phone approval.** Owner only (`forbidden` for mechanics), note required (`note_required`, ≤ 500 chars), same version check. Stored as `actor_type='staff'`, `actor_id` = owner, `channel='phone'`. Link approvals are `actor_type='customer'`, `channel='link'`. Staff timeline: "Phone approval recorded by ⟨name⟩ — v2, €75.60 — ⟨note⟩". Public timeline: "Approved by phone (recorded by the garage)", no staff name (whitelist).

**D-052 — Decline, cancel, rework.** Customer decline: `quoted → declined`, optional reason in the event note. Staff re-quote: `declined → quoted` (≥ 1 line). Cancel: owner only, from any status except `collected`/`cancelled`, reason required; final. Rework: `ready → in_progress`, owner or assigned mechanic, optional note. Revenue and the open-job workload exclude `cancelled`; `declined` counts as open.

**D-053 — Links never expire.** A link is valid until revoked or regenerated (D-039). Links can be created/regenerated while `quoted`, `declined`, `approved`, `in_progress` or `ready`; an existing link keeps working in every status and shows the current one. Approve/Decline only act while `quoted` and on the shown version.

**D-054 — Mechanics create customers, vehicles and jobs.** RLS: active staff can select, insert and update customers and vehicles; delete is owner only. Mechanics see the whole customer/vehicle directory, so they can find an existing car instead of creating a duplicate (plates are unique) — accepted for a 4-person garage. A `jobs` before-insert trigger forces `assigned_mechanic_id = auth.uid()` when the caller is a mechanic; changing `assigned_mechanic_id` later is owner only. Jobs, lines, quotes and events stay per assignment (D-020 still applies to `/dashboard` and `/settings`).

**D-055 — Locale.** EUR, garage timezone Europe/Sofia, English UI. Money is shown as `€1,234.56` (en-IE). Money input accepts `1234.56`, `1234,56`, `1,234.56`, `1 234,56` with an optional `€`, and rejects more than 2 decimals or ambiguous input. Phones are stored as digits; a national `0…` 10-digit number becomes `359…`, shown as `+359 88 123 4567` and used as-is for `wa.me`. Plates display as `CA 1234 AB`.

**D-056 — Revenue.** `get_dashboard` revenue = Σ `approved_subtotal_cents` (net) of `collected` jobs whose `collected_at` falls in the current calendar month in Europe/Sofia. The dashboard shows net only (`revenue.net_cents`), per the client.

**D-057 — Line edits that re-quote need a staff author.** The re-quote trigger (D-050) raises `forbidden` when there is no staff caller, so the service role cannot change lines of a `quoted`, `approved` or `in_progress` job (the new version would have no `created_by`). Scripts edit lines only while the job row is `new` or `declined`. The line guard locks the job row `FOR UPDATE` (not `FOR SHARE`): the statement trigger re-quotes under the same lock, and two concurrent edits of one job queue instead of deadlocking on a lock upgrade.

**D-058 — Existing quotes become version 1.** The migration backfills every already-quoted job with `quote_version = 1` and a `job_quotes` v1 row (snapshot of its current lines, dated `quoted_at`, author `created_by`); approved jobs get `approved_quote_version = 1` and `approved_subtotal/vat_cents` from the frozen `quoted_*`. The `quoted_*` and `approved_*` column groups are all-or-none (check constraints).

**D-059 — Customer decisions are version-bound and idempotent.** Decline, like approve, must pass the version shown (`quote_changed` otherwise); both are stored with `channel = 'link'`, the version and its total. Repeating the decision already taken on the same version (double tap) returns the current job and writes no event; anything else outside `quoted` is `invalid_transition`. Starting, finishing or handing back a job whose current version is not the approved one is also `invalid_transition` (no extra error code). `job_events.channel` may be set only on `approved`/`declined` events.

**D-060 — The public page shows the quote the customer decides on.** `public_job_by_token_hash` takes lines and totals from the `job_quotes` row of the job's current version, not from live lines, so a page always matches the version its buttons send. The DTO adds `job.quote_version` and `timeline[].channel` (whitelist updated in `PUBLIC_JOB_KEYS`).

**D-061 — Seed writes each job's history directly.** As in D-016/D-024, the seed (service role) builds every job while its row is still `new` (lines, then each quote version from `job_totals` and a line snapshot), inserts the backdated events (versions, channels, notes), `job_quotes` rows and links, then sets the final status and frozen figures in one update. Every quoted job gets a link row (the customer was sent one); only the demo links are printed. Staff display names are Bulgarian; the 4 login emails stay as they were. The client-answers migration sets the settings singleton to the demo garage (€45.00/h, 20% VAT, Europe/Sofia, EUR) so a fresh database matches the seed.

**D-062 — Customer + first vehicle in one call; delete takes the vehicles.** `create_customer(...)` (security invoker, so RLS applies) inserts both rows in one transaction; a duplicate plate leaves no orphan customer. `vehicles.customer_id` is `on delete cascade`, so the owner deletes a customer with their vehicles; `jobs.vehicle_id` still restricts, so a customer with any job cannot be deleted (23503 → "This customer has jobs, so they can't be deleted.").

**D-063 — Phone search accepts the national format.** `search_customers` strips non-digits and one leading `0` from the query before the phone substring match, so "0888 123" finds a number stored as `359888123…`.

**D-064 — Supabase advisor WARNs on security-definer RPCs are accepted.** `transition_job`, `create_job_link`, `revoke_job_link` (and later staff RPCs) are callable by `authenticated` on purpose: they are the only write path for status, links and quotes, and each one checks the caller itself before reading or locking anything (`private.staff_role()`, assignment, owner-only paths; D-038, D-039, D-051). `anon` has no EXECUTE on them. `rate_limits` has RLS with no policies by design (service role only). Unused-index INFO notices are expected before real traffic.

**D-065 — Remote operations without a linked CLI.** The CLI account on this machine has no Management API rights on the client project, so migrations go to the remote with `supabase db push --db-url` through the session pooler (`aws-0-ap-northeast-1`), always from a clean worktree of the pushed commit so uncommitted migration files are never applied. Auth settings (sign-up disabled, 12-char lower/upper/digit passwords, reauthentication for password change, site URL) and advisors use the Management API with the owner's access token from `.env.local`; `supabase config push` is not used because `config.toml` holds local-only values.

**D-066 — Vercel functions run in `hnd1` (Tokyo).** The Supabase project is in `ap-northeast-1`; every page does several DB round trips, so the function region sits next to the database (`vercel.json`). Users in Sofia pay one long round trip per request instead of one per query. A real launch should move the database to `eu-central-1` and the functions to `fra1` (NEXT-STEPS).

**D-067 — Signed-in staff cannot decide on a customer link.** Approve/Decline on `/[token]` refuse with "You're signed in as garage staff — record a phone approval from the job page instead." when the request carries an active staff session, before any rate-limit or database call. Otherwise a mechanic could open a link they created and record a "customer" approval. Residual risk, accepted: a staff member who opens the link signed out (private window, another device) is indistinguishable from the customer. We deliberately do not store IP addresses or device fingerprints to tell them apart (GDPR, EU client); the link token, the version-bound event and the staff audit trail (who created the link, when) are the controls.

**D-068 — Decisions are priced from the quote row.** Approval copies `subtotal/vat/total_cents` from the `job_quotes` row whose version equals `p_expected_version`, and approve/decline events take their version and total from that row, not from `jobs.quoted_*`. The frozen quote is the single source; a drift in the job's cached columns can never change what was approved.

**D-069 — Column-level write grants for customers and vehicles.** `authenticated` may insert/update only `customers (full_name, phone, email)`, insert `vehicles (customer_id, plate, make, model, year)` and update `vehicles (plate, make, model, year)`. Ids, timestamps and moving a vehicle to another customer are refused (42501). `create_customer` (security invoker) uses exactly these columns.

**D-070 — No-op line saves don't re-quote; length limits in the database.** The re-quote trigger ignores updates where description, quantity and unit price are unchanged (a labour price change is already pinned by the line guard), so saving an unchanged form never asks the customer again. CHECK constraints mirror the server-action limits: customer name ≤ 200, phone 6–15 digits (after normalisation), email ≤ 200, plate 2–10 characters, make/model ≤ 60, job description ≤ 2000, line description ≤ 500 (event notes were already ≤ 500). Settings text has no app form yet, so no limit was added there.


**D-071 — Closed customer links are rejected in the proxy, before render.** In Next 16, `notFound()` thrown in a page during a dynamic render escapes the React shell and Next answers with an empty `__next_error__` shell that only shows "Page not found" after JS runs (and with different headers from an unmatched URL). So `src/proxy.ts` does the decision first: outside the app routes (`/`, `/login`, staff prefixes) only `/{token}` can exist; it runs the same `publicView` rate limit and `getPublicJob` lookup as the page and, when closed (or for any deeper unknown path), rewrites to an unmatched path so Next serves the server-rendered `/_not-found`. Bad link, unknown single- and multi-segment URLs now get byte-identical bodies and identical headers (incl. `x-middleware-rewrite`). Requests carrying `next-action` skip the gate (the action checks the token and has its own limit). The page keeps its `notFound()` as a fallback but no longer rate-limits itself, so a view counts once against `publicView`.

**D-072 — Settings page (FR9).** Owner only: the page calls `requireOwner()` (mechanics get the generic 404), the action re-checks the role, and the write goes through the owner's session so RLS `settings_update` and the column grant are the real guard. The rate is parsed with `parseMoneyToCents` and must be above €0; VAT with `percentToBps` (0–100 %, up to 2 decimals). A new rate applies to every labour line added from now on, including on jobs already open; a new VAT rate applies only to jobs created from now on (each job keeps the `vat_bps` copied at creation). Both are existing DB triggers (FR4), so the page only explains it. Garage name ≤ 100, address ≤ 200, phone ≤ 30 characters are checked in the action only; there is one owner-edited row, so no DB constraint was added. The e2e spec runs in the desktop project only: the settings row is global and the two projects would race.

**D-073 — Production deploys from the CLI, URL garage-desk-tau.vercel.app.** The Vercel project is linked to the GitHub repo but has Git deployments disabled (`createDeployments: disabled`); we did not change that project setting. Production is deployed with `vercel deploy --prod` from a clean `git worktree` of the pushed commit, so only committed files are uploaded and local `.env*` files never leave the machine. `garage-desk.vercel.app` belongs to someone else; Vercel assigned `garage-desk-tau.vercel.app`, which is set as `NEXT_PUBLIC_SITE_URL` (production) and as the Supabase Auth site URL. Preview deployments fall back to the request origin for customer links.

**D-074 — Visual redesign to the client's reference dashboard (docs/DESIGN.md).** Floating app frame on a grey canvas, black primary action, Inter self-hosted via `next/font`. Where we differ from the reference, and why: status and meta colours use the 700 shades and faint text is `#6e6e77` (not `#71717A`) so every text pair is at least 4.5:1, and input borders are `#8e8e95` (3:1, heavier than the reference); on the grey canvas (customer link page) meta text uses `muted`, because `faint` drops below 4.5:1 there. No illustrations, AI button, bell or plan card: their slots hold real features (sidebar counts, recent jobs, revenue or "my open jobs" card). KPI footers state real facts, never deltas; the revenue KPI reads "Revenue this month" with a "net" suffix on the figure so it fits four across. The dashboard "View" link in the ready table repeats the job-ref link for mouse users only (`tabIndex=-1`, `aria-hidden`); line Edit/Delete became icon buttons with the full accessible names so the line table fits beside the side panel. The frame's data (`src/lib/data/shell.ts`) uses the signed-in user's client, so RLS limits a mechanic's counts and recent jobs to their own; owners share one `get_dashboard` call per request with the dashboard page through React `cache`.

**D-075 — Deploy from a `git archive`, not a worktree.** Vercel Hobby blocks a deployment whose git commit author is not the account owner (`TEAM_ACCESS_REQUIRED`); the commits are authored with an email that is not linked to the `kurtgav` Vercel account, so worktree deploys (which carry git metadata) came back `BLOCKED`. Deploying an export of the pushed commit (`git archive HEAD`, no `.git`) attributes the deployment to the CLI user `kurtgav` and still uploads only committed files. History was not rewritten. Lasting fix: add the commit email to the `kurtgav` Vercel/GitHub account or commit as that account (NEXT-STEPS).

**D-076 — Own profile fields; colleagues never read phone or about.** `profiles` gains `phone` (≤ 30), `about` (≤ 500), `avatar_path` and `updated_at` (trigger), and `full_name` is capped at 100 now that staff edit it. `authenticated` may update only `full_name, phone, about, avatar_path`, and only on its own active row (`profiles_update_self`); `role`/`active` have no client grant (42501). Select is column-level too: `id, full_name, role, active, avatar_path, updated_at` — enough for timelines, pickers and photos — so `phone`/`about` (personal data) cannot be read through the API by anyone, owner included. The signed-in user's own phone/about are read server-side with the service role, keyed by the verified session user only (`getMyProfile`). `avatar_path` must match `{own id}/{random}.{png|jpg|webp}` (CHECK), so a profile cannot point at a colleague's file. `select("*")` on profiles from a user client now fails; select named columns.

**D-077 — Staff management: activation through an owner-only RPC, Auth admin only for Auth.** `set_staff_active(p_profile_id, p_active)` (security definer, `authenticated` only) refuses non-owners (`forbidden`) and self (`cannot_change_self`) before taking an advisory lock, then refuses unknown ids and any change that would leave no active owner (`last_owner`); the lock makes that check see a concurrent deactivation, so two owners cannot deactivate each other at the same moment. Deactivation also deletes the user's `auth.sessions` (refresh tokens cascade), so every device is signed out at once and a later reactivation does not revive old sessions; access tokens already issued stay valid until expiry (≤ 1 h) but RLS and `getStaff` refuse them because `profiles.active` is false. The function owner (`postgres`) needs DELETE on `auth.sessions`. The `/staff` actions call it with the owner's session, then use the service role only for Auth: a 100-year ban on deactivation (no new sign-in), `ban_duration: none` on reactivation, `createUser` (confirmed, mechanic profile; the Auth user is deleted again if the profile insert fails) and password resets for mechanics only — an owner's password is never reset from `/staff` (it would bypass their password); owners use `/profile` or forgot password. Temporary passwords are 16 characters from a look-alike-free alphabet (~93 bits), always meeting the Auth rule, returned once and never stored or logged. Not done: forcing a password change after a temporary password; reassigning a deactivated mechanic's open jobs (the owner does it on the job). Seed, e2e and integration setup keep writing `profiles` with the service role directly (like D-016), outside these guards.

**D-078 — Avatars: private bucket, signed URLs, server-side sniffing.** Bucket `avatars` (private, 2 MB, PNG/JPEG/WebP only, so SVG is refused by Storage too). Storage RLS: active staff read every photo; insert/update/delete only under `{auth.uid()}/` — not even the owner writes into another folder. Uploads go through a server action (`serverActions.bodySizeLimit` raised to 3 MB for multipart overhead) that checks size, the declared MIME and the file's magic bytes, stores it as `{uid}/{uuid}.{ext}` with the sniffed content type, points the profile at it and then deletes the old file (best effort; an orphan is unreferenced and staff-only). Pages get 10-minute signed URLs signed with the viewer's session; CSP `img-src` adds the Supabase origin.

**D-079 — Password recovery: neutral form, token-hash link, recovery-only reset page.** `/forgot-password` always answers the same after validation (no account enumeration) and is limited to 5 requests per 15 minutes per client (hashed IP, D-012); Auth's own per-address limits apply on top. The email is requested in `after()` (once the response is sent), so the answer takes the same time for known and unknown addresses. The email template (`supabase/templates/recovery.html`, remote via the Management API) links to `{{ .SiteURL }}/auth/confirm?token_hash=…&type=recovery`; the route verifies it (`verifyOtp`) into a session and sends bad, used or expired links to `/forgot-password?expired=1`. The boundary for password changes is Auth itself (`secure_password_change`: a session older than 24 h must reauthenticate; shown as "Please sign in again to change your password"). On top of that, as app-layer defence in depth: `/reset-password` accepts only a session from such a link opened within the last hour (JWT `amr` `otp` with its timestamp, checked with `getClaims`), so a normal password session cannot use it to skip the current password; and `/profile` re-checks the current password on a throwaway client (its session is signed out right away) before updating through the user's own session, so Auth signs out their other sessions. Known limits: a mail scanner that opens links can use up the one-time token (the user then requests a new one); in production the built-in mailer reaches only the project team, so real staff need custom SMTP or the owner's reset on `/staff`.

**D-083 — Staff photos are plain `<img>` from short-lived signed URLs, initials otherwise.** The `avatars` bucket is private, so the server hands the page a signed URL that expires within minutes; `next/image` would cache and re-serve it past expiry and adds nothing for a 36–80 px circle, so `src/components/avatar.tsx` renders a plain `<img alt="">` (lint rule disabled on that line only). The avatar is decorative (`aria-hidden`): the name is always next to it. Without a photo it shows the initials of the first two words of the name. On `/profile` a chosen file is checked in the browser (PNG, JPEG or WebP, ≤ 2 MB, mirroring the bucket and the action, which re-checks size, MIME and magic bytes) and previewed from a local object URL; nothing is uploaded until "Save photo", and the preview is dropped after the action returns.

**D-084 — Temporary passwords live only in the dialog that produced them.** `createStaff` and `resetStaffPassword` return the password once; the UI keeps it in that dialog's action state and nowhere else (no URL, storage, toast or log). The form is rendered inside `DialogContent`, which unmounts on close, so closing the dialog discards the password and the next open starts a fresh form. The owner gets a read-only field, a Copy button and the instruction to share it privately and have the person change it on their profile. Reset is offered only for active members (a deactivated account cannot sign in; reactivate first). The `/staff` page shows no row actions on your own row (it links to `/profile` instead) and no Deactivate on the last active owner; the actions and DB guards enforce the same rules, so this only avoids offering a button that would fail.

**D-085 — Role-dependent UI is decided on the server; mechanics' empty states say whose jobs they are.** Owner-only controls come from server-computed flags (`job.can.*`, `customer.canDelete`, `requireOwner()`, `staff.role` in the layout), never from client state, so there is no flash of owner UI and the HTML a mechanic receives holds no owner controls. Owner-only pages (`/dashboard`, `/settings`, `/staff`) give mechanics the generic 404 with a role-aware title ("Page not found"), like `/jobs/[id]` for someone else's job. Because a mechanic only sees their own jobs, their empty states name that ("No open jobs assigned to you", "No jobs assigned to you" on a customer), so an empty list is not mistaken for "the garage has no jobs". The per-page checklist is in docs/DESIGN.md.

**D-080 — The public pages copy the reference's visual language, scoped away from the staff app.** The client asked for the landing page to reverse-engineer https://boxinside.webflow.io; its tokens, type, shapes, section rhythm and motion are reproduced (docs/DESIGN.md "Landing page") with Garage Desk's own content. Plus Jakarta Sans and Figtree (the reference's faces) come through next/font, so they are self-hosted (CSP `font-src 'self'`) and only load on the public pages (the class is set on their wrapper, not on `<html>`). All styles are `lp-*` tokens or rules under `.lp`, added in a marked section of `globals.css`, so the staff app's tokens and Inter are untouched. Kept from the reference for fidelity although generic elsewhere: section eyebrows with a short rule, the soft shadow on the hero tile. Not copied: testimonials, customer logos, counts, ratings and prices, which would be invented; their slots hold the security rules and the product tour.

**D-081 — The password reveal toggle has a fixed name and reports its state with `aria-pressed`.** `PasswordInput`'s button is named "Show password" (visually hidden text, not `aria-label`) whether or not the password is shown, and `aria-pressed` says which, following the WAI-ARIA toggle-button pattern; a name that flips between "Show" and "Hide" would announce the opposite of the state. Using text content rather than `aria-label` keeps `getByLabel("Password")` matching only the input. A second field on the same form gets its own name (`toggleLabel="Show confirmation"`). Pointer presses keep focus and the caret in the input; the right padding for the button is always reserved, whatever `className` the caller passes.

**D-082 — Scroll reveals only hide content once JavaScript runs; landing images are pre-optimised.** `[data-reveal]` elements start hidden only under `.lp-js`, a class the `Reveal` client component adds after hydration (skipped under `prefers-reduced-motion`), and anything already on screen is marked in at once, so the page is complete without JavaScript, for crawlers and with reduced motion. No inline script (nonce CSP). Screenshots in `public/landing/` are resized WebP copies of `docs/screenshots/`, served through `next/image` (same origin, `img-src 'self'`); the hero's phone is the LCP image (`preload`). The customer-page screenshot is cut just above the sticky approve bar (the source capture has the bar half over the Total row), and files are renamed whenever their content changes so the image optimiser cache cannot serve the old crop.

**D-086 — Production password-reset emails wait for custom SMTP; the owner's reset on /staff is the working path.** The Management API refuses to change email templates on a free-tier project that uses the built-in mailer ("Email template modification is not available for free tier projects using the default email provider"), and the built-in mailer only delivers to the Supabase project's team addresses anyway. So on production the recovery email still uses Supabase's default template, whose link does not match our `/auth/confirm?token_hash=…` route (D-077), and staff addresses receive nothing. The forgot-password page keeps its neutral answer and adds "No email after a few minutes? Ask the garage owner to reset your password from the Staff page."; the landing FAQ says the same. Locally (Mailpit) the full flow runs and is covered by e2e. When the garage configures SMTP, apply `supabase/templates/recovery.html` with the subject "Reset your Garage Desk password" through `PATCH /v1/projects/{ref}/config/auth` (`mailer_subjects_recovery`, `mailer_templates_recovery_content`); see docs/NEXT-STEPS.md.

**D-087 — Rate limits key on `x-forwarded-for` because Vercel overwrites it.** `src/lib/rate-limit.ts` takes the first `x-forwarded-for` entry. On Vercel the edge replaces that header with the real client IP and drops any value the client sent, so it cannot be spoofed in production; locally it can, which the e2e suite uses to give each simulated user its own IP. If the app ever runs behind another proxy, this must change to that proxy's trusted header. Consequence for production e2e: all runs share one IP, so they stay under 10 sign-ins per 5 minutes or wait between runs.

**D-088 — Sign-in pages: rectangle controls, and notices that stay put while a retry is pending.** On `/login`, `/forgot-password` and `/reset-password` the fields and the submit share one 48px, 12px-radius rectangle family that matches the card, instead of the landing's pill buttons; the landing keeps its pills. Action results show in `AuthNotice` (`src/components/landing/auth-notice.tsx`): it animates its height open, keeps the last result visible while a retry is pending (the earlier "unmount while pending" made the form jump up and down on every retry), and remounts the alert on every new result (keyed by a result counter) so a repeated message is still announced. The reveal toggle in `PasswordInput` keeps its full-height hit area but draws its focus ring inside the field (`outline-offset: -6px`) and transitions only `color`, so the ring never spills past the field or fades in from grey; this also applies on the staff profile page.

**D-089 — Production deploys skip Vercel's build cache (`vercel deploy --prod --force`).** The first Phase 5 deploy served the previous build's stylesheet: the new landing and sign-in styles in `globals.css` were missing from the deployed CSS although the uploaded source and a local `pnpm build` both had them, so the restored build cache produced stale CSS. Redeploying with `--force` (no build cache) fixed it. Every production deploy in the D-075 procedure now passes `--force`; the build takes about a minute longer. After a deploy, the landing e2e (axe contrast on the blue sections) catches a stale stylesheet.

**D-090 — Every dashboard figure links to the jobs it counts; `/jobs` takes `mechanic` and `period=month`.** Each KPI card, its footer fact (in progress, declined quotes), each ready row and each workload card and status chip opens `/jobs` filtered to exactly those jobs, through one stretched link per card or row (no nested links; footers and chips sit above it with `z-10`). Revenue opens `/jobs?status=collected&period=month`. That month is computed in TypeScript (`src/lib/period.ts`, Europe/Sofia wall clock) rather than by a new RPC, and `tests/integration/dashboard-period.test.ts` holds it to `get_dashboard`'s `month_start`/`month_end` (D-027) across DST and month boundaries, so the list count always equals the KPI's "N jobs collected". The garage timezone is the fixed `GARAGE_TZ` here; if settings ever make the timezone editable, that test fails until the helper reads it too. `period` is honoured only with `status=collected`, `mechanic` only for the owner (mechanics' RLS already limits them to their own jobs) and only when it names an existing mechanic; any other value is dropped, never an error. Filters show as removable chips and the status tabs keep the mechanic filter.
